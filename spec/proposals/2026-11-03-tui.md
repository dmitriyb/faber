# Change Proposal: TUI — a live view over the journal, as a new module

## Context

Every surface faber has is a line printed once: the progress stream during
a run, the report after it, the `runs` table on request. None of them can
answer the questions an operator has while a run is alive — where is it
now, since when, is that step stuck, what is it waiting for, what did the
box print — without the operator correlating three outputs by hand. The
pipeline spec reserved this seam from the start ("a live view is this same
reporter over a journal that hasn't stopped growing"), and the four
preceding changes built everything such a view reads: typed progress
events, durable step starts, per-attempt `output.log`, loop rollups and the
human vocabulary, hold reasons, expected counts.

The design was settled against rendered mock-ups of four screens at the
operator's real terminal size and theme, and against three rules that keep
the view honest: it shows nothing the CLI cannot show, it does nothing the
CLI cannot do, and every action names the command it runs. Plain ASCII
only, one cell per character; colour as an additive layer on the 16 palette
slots so the terminal theme owns every colour; bold magenta for chrome,
blue for identifiers, the status column coloured by meaning, bright black
for what is not part of the story.

## Proposed change

- **A new module, `tui`.** Depends on config, failure, and pipeline, after
  pipeline in the dependency order; registered in `spec/project.json` with
  its own `spec/tui/` directory and a milestone. It is a reader: it never
  executes a run in-process and never holds state the journal does not.
- **Entry.** Bare `faber` on a terminal opens the TUI on the current
  directory's config and the host's run store (off a terminal, bare `faber`
  stays the usage error). `faber watch [<run-id|name>]` opens it explicitly,
  on a run when given. The root command dispatches through a `UI` seam on
  the CLI's `Deps`, so config never imports the module; the cmd wiring fills
  it. The TUI runs `--help`-free: it reads the same flags `run` takes for
  colour (`--color`), and the terminal probe decides the rest.
- **Home.** Two panes and a footer, exactly the rendered screen: the
  project (workflows with their params, `config valid` or the validation
  error, every template with whether its image is in the daemon — the run
  preflight shown before anyone presses run) and the runs of this config
  from the store (`faber runs` as a table: id, name, workflow, state,
  started, wall, and the live run's current step), other configs' runs
  folded below. The selected run's `now`, `last`, `next` lines underneath.
  Keys: enter opens a run; `r` starts a workflow (a parameter prompt, then
  `faber run …` spawned as a detached child whose stderr goes to the run
  store's `logs/` directory, and the new run is followed through the
  journal); `p` writes the pause marker through the run controller; `R`
  spawns `faber resume …`; `q` quits. Prune, upgrade, and key management
  stay CLI-only.
- **Run.** Header with id, state, workflow, params, started, wall; a now
  and next strip; three panes — STEPS, STEP, OUTPUT — and four views over
  the selected step switched by one key: `tree` (the report's loop-aware
  reading order: finished cycles one line each with their composition, the
  active or failed iteration open, aligned status column, full-row
  selection), `graph` (the collapsed DAG drawn in ASCII: longest-path
  layering, one barycenter pass, orthogonal edges, columns are dependency
  depth, idle nodes name what they wait on; collapsed to per-layer
  summaries above sixty drawn nodes), `output` (the attempt's `output.log`
  tail), `timeline` (one row per cycle with step letters, expandable to one
  row per executed attempt, a time axis scaled to the width, bars coloured
  by status). STEP shows the breadcrumb, state, reason, attempts, duration
  against the median of that step name across every journal in the store
  (`usually 4m10s`, yellow past twice), template, inputs, error, handoff,
  the re-enter or resume command, and sessions. Keys: `j`/`k` move, `n`
  jumps to the next FAIL, HALT or WAIT, `/` filters, `f` follows the newest
  active step, `enter` expands, `q` goes back and prints the selected
  command on stdout so it sits on the next prompt line.
- **Liveness.** The view reloads the journal (and the output tail) at one
  hertz and on input, derives "running since" from a start without a later
  result, reads loop caps and expectations from the IR and the journal,
  and rings the terminal bell once when a step settles FAIL or HALT, a defer
  begins, or the run pauses. A run started by another process is watched
  the same way; the `run.lock` probe is what makes it `LIVE`.
- **Renderer.** Our own, over `x/term`: raw mode, size from `GetSize`,
  full-frame redraw into a buffer and one write, resize honoured on the
  next frame, restore on every exit path. Colour only through the role
  table and only when the probe allows. The four mock screens rendered
  during design, stripped of colour codes, are checked in as fixtures the
  renderer's golden tests compare against at 221×51 and 80×24.
- **Out of scope.** Editing configuration, a diagnostic-log viewer, metrics
  dashboards, mouse support, any animation beyond the ticking elapsed
  counters, running a workflow inside the TUI's process.

## Impact expectation

- **tui** (new): the module — data loading over the store, the reporter and
  the IR; the four views and Home; the renderer and the key loop; the
  detached-child spawning; golden fixtures and tests.
- **config**: the `UI` seam on `Deps`, the root command's terminal
  dispatch, the `watch` subcommand; docs.
- **pipeline**: an exported attempt-directory helper so the TUI finds
  `output.log` without re-deriving the path token; no behaviour change.
- **cmd**: the wiring fills the seam with the store, the docker client, and
  the image tagger it already has.
- **spec**: `spec/project.json` gains the module and an Observability
  milestone; `spec/tui/` holds the module file and its leaves; the pipeline
  reporter's deferred observability requirement is narrowed to what still
  remains (traces).
